## Preregistered conditions and acceptance

CONTROL is the frozen `Releases/Zepholume-Shaders-1.0.5.zip`, SHA-256 `4B3803CF87AF43952CF91D145BB634C3346DEF6FC8C7008C37368058DC75DC91`, relative to the Git root. TREATMENT is project `dist/Zepholume-Shaders-1.0.6-dev-phase3.zip`, SHA-256 `8BC997B1CDBCB17ABF5D583E76B09B2E427873B2A24CA1B30D593EEBF5CB85B5`. If either identity changes, preregister a new series before looking at outcomes. Preserve every original export, rejected run and stated rejection reason.

Start with 1.20.1 Fabric/Iris Balanced, then water-heavy Balanced, then the same two scenes on Ultra and Potato. Expand Low/High and Oculus after primary correctness qualification. Each loader, profile, scene, GPU and resolution is a separate series. Capture at least six CONTROL/CONTROL pairs before eight CONTROL/TREATMENT pairs, alternating CT, TC, CT, TC. The existing analyzer enforces these counts, exceeding the requested three samples per candidate. Frames within a run are correlated; the run/pair is the replication unit.

Before any candidate measurements, set guardrails: median frame-time regression over 3%, or either p95/p99 regression over 5%, requests investigation and blocks performance acceptance if repeatable and larger than the observed corresponding A/A noise envelope. An A/A envelope at or above a guardrail makes that gate **INCONCLUSIVE**, requiring reduced noise and a fresh complete series. Positive deltas below a threshold are not proof of equality. An improvement requires a negative paired median outside observed noise, consistent paired behavior, unchanged visual correctness, and review of drift and tails. The existing analyzer describes deltas; these guardrails are a review policy, not an implemented automatic PASS. Do not weaken the analyzer to obtain acceptance.

## Matched scenes and recording

Create one disposable creative test world; record actual seed, dimension, exact coordinates, yaw/pitch, fixed time/weather, world snapshot SHA-256 and stationary camera specification in the existing scene manifest. Do not invent these values before the world exists. Freeze a separate initial snapshot per scene and restore only the disposable test world between runs. Preload chunks; exclude reloads, chunk generation, menus and compilation from the measured window.

Use two primary fixed viewpoints: terrain with mixed lit/shaded stone, foliage and transparent blocks at clear noon; and a shoreline with both shallow/deep water and distant terrain at clear noon. Keep stationary during measurements; waterline crossings belong in visual QA. Extend later to a torch-lit cave, midnight, rain, Nether and End using separately frozen conditions. Matched screenshots must demonstrate the same geometry and lighting conditions in both packs before timing acceptance.

For every run: at least 30 seconds warm-up after settling, then 60 seconds capture. Lengthen both consistently for the entire series if clocks or chunks have not settled. Record GPU/driver, Java build/JVM arguments, all mod versions and hashes, game/loader, OpenGL backend, resolution/render scale, render/simulation distance, FOV, mipmaps, texture filtering, resource packs, shader settings, VSync, FPS cap, and power/thermal/background-process conditions. Use VSync off and a fixed uncapped measurement configuration; preserve the operator's unrelated instances. In 1.21.11 and 26.3 record new vanilla quality/texture-filtering options explicitly rather than assuming names/defaults match 1.20.1.

Use an available presentation-frame capture tool only after validating that it captures this OpenGL Minecraft process and documenting its version, original field names, units, capture-loss behavior and timestamp semantics. GPU timer query duration, JFR aggregate FPS and an F3 screenshot are insufficient substitutes for raw presentation frame intervals. Do not install another tool solely to fill an empty results table. List clocks/temperature/CPU/GPU busy telemetry as unavailable when the recorder cannot supply it; do not infer bottlenecks from FPS alone.

The adapter CSV schema is one row per captured presentation interval, invariant-culture positive finite milliseconds, header `frameTimeMs`. Keep raw recorder exports beside it and document conversion; never synthesize samples from average FPS or silently trim outliers. Complete one schemaVersion 2 run manifest per CSV using the existing template. Its `captureTool.rawFrameTimeSha256` binds the converted data; keep hashes of the originals as companion evidence. Missing/dropped intervals, mismatched conditions, overlapping captures or unexplained thermal drift invalidate a run; fix the cause and rerun the affected preregistered series.

## Analysis and handoff

From the project directory, execute with PowerShell 7:

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -File scripts/benchmark-series.ps1 -SeriesManifest <capture-directory>/series.json -OutputJson <capture-directory>/comparison.json
```

Report per-run and paired median/p95/p99 milliseconds, average FPS, population frame-time variance/standard deviation, all paired percentage deltas, A/A envelope, sample/run counts, rejected runs and missing telemetry. `onePercentLowFps` in the existing summary is explicitly a legacy alias for `1000/p99`; label it **inverse-p99 FPS**, not the mean of the slowest 1% of frames. If a mean-slowest-1% metric is required, compute and name it separately from preserved raw data with a documented convention. Do not conflate the two.

The A/A envelope is descriptive, not a confidence interval. When claiming a performance difference, report a run/pair-level uncertainty estimate using a declared method, or state that a credible uncertainty estimate is unavailable and the result remains inconclusive. Do not bootstrap individual frames as independent trials. Retain captures, manifests, screenshots, logs, patched shaders and comparison JSON for independent analysis. No performance acceptance follows from a parser/test pass.
